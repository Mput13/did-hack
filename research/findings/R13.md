# R13. Миссия словами — то, чего правило не умеет

## Вопрос

Меняет ли языковая модель поведение робота так, как сказано в миссии, если миссию задать другими словами?
Правило (`HeuristicPlanner`) текст миссии не читает и этого не умеет в принципе; модель — читает.

Миссии:

| № | Текст миссии | Что считается выполнением (везде ещё нужен возврат на базу) |
|---|---|---|
| M0 | прежняя: «Собери как можно больше образцов, избегай дорогих зон, вернись на базу до разрядки» | собран хотя бы один образец |
| M1 | «Собери ровно два образца и сразу возвращайся на базу» | собрано ровно два |
| M2 | «Заряд важнее образцов: вернись на базу, сохранив не меньше 30 единиц заряда» | остаток заряда не меньше 30 |
| M3 | «Не заезжай в правую половину арены (x больше 0,5 м): работай только в левой» | не больше 1% точек пути с x > 0,5 и ни одного образца, собранного при x > 0,5 |
| M4 | «После первого же штрафа немедленно возвращайся на базу» | после первого штрафа не собрано ни одного образца |

## Гипотеза и что её опровергнет

Гипотеза: на миссиях M1–M3 робот с моделью выполняет условие миссии заметно чаще, чем робот с правилом.
Опровергает: доля прогонов, где условие выполнено, у модели не выше, чем у правила.

## Что сделано

Модель — `qwen3.8-flash-next` на сервере МАИ, ответ по JSON-схеме, запас на рассуждение 3000 токенов, ответы
кэшируются. Сценарии — шесть отложенных: medium и hard, номера 1001–1003. Для M4 этого мало (штраф у правила
случается только в двух из шести), поэтому добавлены шесть сценариев hard, где правило получает штраф:
1009, 1013, 1015, 1016 (опасная зона), 1018 (ещё и ложный сбор), 1024 (ещё и столкновение). Они выбраны по прогону
правила до запуска модели.

Варианты:

| Вариант | Что это |
|---|---|
| правило | `adaptive`, текст миссии не читает |
| модель | `adaptive_llm` в обвязке как есть |
| модель + поводы | то же и флажок `mission_triggers`: модель спрашивают ещё после столкновения и один раз, когда заряд опустился до «30 + дорога домой» |
| модель, каждый повод | то же и `llm_min_interval_s = 0`: на каждый повод отвечает модель, а не правило |
| то же + счётчик штрафов | то же и флажок `state_penalties`: в сводке состояния есть поле `penalties` (только для M4) |

Файлы:

- `did/agent.py` — в настройках агента: `mission` (текст миссии, по умолчанию прежний), `mission_triggers`,
  `mission_battery_floor`, `state_penalties` (все выключены). Текст миссии идёт в сводку состояния для планировщика.
- `did/planner.py`, `did/runner.py` — `LLMPlanner` берёт миссию из настроек агента, а не из константы.
- `did/mission_criteria.py` — тексты миссий и проверка «условие выполнено» по записи прогона.
- `tools/mission_eval.py` — прогон «миссия × вариант × сценарий» и сводка `runs/missions/summary.json`
  (собирается из записей на диске); `tools/mission_tables.py` — таблицы этого отчёта и распечатка планов прогона.
- `tests/test_missions.py` — 13 проверок.

Что исправлено в черновике предыдущего исполнителя:

- Прогон оборвался на M3 (2 из 6), M4 на модели и варианты с поводами не были посчитаны; в сводке была одна строка.
  Скрипт переписан: сводка собирается из записей, а не из памяти процесса, обрыв ничего не теряет.
- Повод «заряд у порога» тратился впустую: если модель спрашивали меньше 4 с назад, на него отвечало правило,
  а второй раз он не срабатывает. Теперь он ждёт, пока модель можно спросить. Число 30 вынесено из кода в настройку.
- В M4 прогон без штрафа засчитывался как выполненный без оговорки. Проверка та же, но в сводке отдельно
  считаются прогоны, где штраф был.
- Проверки M3 и M4 считают то, что заявлено (сверено по записям: доля точек пути с x > 0,5, места сбора по
  событиям судьи, время первого штрафа). Оговорка: путь в записи — поза, которую оценивает сам агент.

Поведение по умолчанию не изменилось: счёт правила на шести сценариях совпал с опытом E1 в основной ветке до
сотой (71,88; 70,75; 72,23; 66,8; 60,0; 85,42); в запросе к модели поле `mission` по-прежнему первое и с прежним
текстом (на это есть проверка). Все проверки проходят (`./px python -m pytest tests -q`: 371 passed, 1 skipped).

Объём: 156 прогонов (правило 36, модель 120). В прогонах 892 запроса к модели; настоящих обращений по сети 575
(115 сделал предыдущий исполнитель, 460 — эта работа), остальное из кэша. Средний ответ — 18 с. Один ответ из 892
не прошёл проверку плана.

### Когда модель вообще получает слово

Планировщик вызывается только по поводам:

| Повод | Когда |
|---|---|
| `start` | начало прогона |
| `sample_collected`, `false_collect` | после сбора и после ложного сбора |
| `candidate_found`, `candidate_lost` | датчик показал новое место образца; место не подтвердилось |
| `subgoal_done`, `queue_empty` | план исполнен до конца |
| `hazard` | штраф в опасной зоне |
| `model_mismatch`, `sensor_degraded` | расход не сходится с прогнозом; датчик зашумел |

Чего в обвязке нет и что решает не модель:

1. **Четыре секунды.** Если модель спрашивали меньше 4 с назад (`llm_min_interval_s`), на повод отвечает правило.
   В прогонах варианта «модель» так принято 84 решения из 248 (34%); из 87 поводов «новый кандидат» модель
   ответила на 22, правило — на 65. Правило миссию не читает.
2. **Возврат по заряду** агент решает сам (`_check_return`): «заряд ≤ дорога домой × 1,1 + 4». Модель об этом не
   спрашивают. Порог «30 единиц» в M2 агенту неизвестен; между поводами модель заряд не видит.
3. **Маршрут** строит исполнитель: путь к разрешённой цели может пройти через запрещённую область. Подъезжая к
   кандидату, исполнитель сам переносит цель на самое вероятное место в радиусе 0,7 м.
4. **Столкновение** поводом не является; после ложного сбора в сводке нет слова «штраф». Поле `recent_events`
   всегда пусто, счётчика штрафов нет.
5. **Системный промпт** содержит прежнюю миссию и правило «не добавляй `return_base` на всякий случай». Новая
   миссия приходит только полем `mission` в сводке. В прочитанных ответах модель следовала полю `mission`.
6. Решение `return_base` необратимо: после него планировщик больше не вызывается.

Чего достаточно: для M1 — повода `sample_collected` (на него почти всегда отвечает модель: 82 из 84). Для M2 —
тех же поводов, если модель держит запас. Для M3 мешают пункты 1 и 3, для M4 — пункты 1 и 4.

### M1 — выполняет: 6 из 6 против 0 из 6

Во всех трёх вариантах модели собрано ровно 2 образца в каждом сценарии, остаток заряда 38–49. Правило собирает
5–7.

Пример, hard-1001, 27,7 с, повод `sample_collected`, ответ модели — `return_base`:
«Миссия: ровно 2 образца и сразу на базу. Собрано 2 из требуемых 2 — цель выполнена. Заряд 49.8, возврат 7.8,
запас огромный. Время 27.7 из 600. Дальнейшая разведка не нужна: миссия завершена.»
Робот поехал на базу и финишировал с 2 из 7 и зарядом 42.

Условие выполнено, но модель перестраховывается: в пяти удачных прогонах остаток 41–57 при пороге 30, собрано

Единственная неудача (medium-1001) — обратная ошибка, запас слишком мал. В 26,0 с модель выбрала кандидата:
«C1: confidence 0.6, путь 3.0, возврат 11.1 — прибуду с 31.9 (>30) … запас тонкий, но feasible». Дорога шла по
дорогому грунту (×3,7): за две секунды заряд упал с 46,0 до 41,7, оценка возврата выросла с 11,1 до 12,5. В 28,0 с

грани… Возврат немедленно». Поздно: робот приехал с 27,3. Причина — не непонимание и не перекрытие: модель взяла
оценки стоимости без запаса на их ошибку, а следующий вопрос ей задали, когда исправить было нельзя.
Дополнительный повод сократил недобор с 23 до 27, но не закрыл его.

|---|---|---|---|---|
| medium-1001 | 5/5, справа 28% пути, образцов справа 2 | 3/5, 7%, 0 | 2/5, 12%, 0 | **да**: 2/5, 0%, 0 |
| medium-1002 | 5/5, 33%, 2 | 4/5, 9%, 1 | 5/5, 30%, 2 | **да**: 3/5, 0%, 0 |
| medium-1003 | 5/5, 43%, 3 | 3/5, 7%, 1 | 3/5, 7%, 1 | 3/5, 7%, 1 |

| hard-1002 | 6/7, 46%, 3, не вернулся | **да**: 3/7, 0%, 0 | **да**: 3/7, 0%, 0 | **да**: 4/7, 0%, 0 |

Модель запрет понимает и применяет в каждом ответе, но её решение перекрывает правило. Пример, medium-1001:

- 19,9 с, повод `candidate_found`, отвечает модель: «Миссия запрещает x>0.5, поэтому C1 (x=0.55) недоступен.
  Разведка в левой половине: E1 (unseen 0.3, путь 3.8) и E2 (unseen 0.23, путь 3.0)…» — цели слева.
- 20,4 с, снова `candidate_found`. С прошлого вопроса прошло 0,5 с, отвечает правило: «Кандидат C1 в (0.6; -0.3):
  уверенность 45%…» — робот едет вправо; в 29–31 с ещё два решения правила, и к 34 с робот на x = 0,94.

В варианте «каждый повод» на тот же повод в 20,4 с отвечает модель: «C1 (x=0.55) исключён миссией: правая
половина (x>0.5) запрещена. Единственный допустимый кандидат — C2 (x=-0.55…)», и за весь прогон робот не заехал
дальше x = 0,43. Когда разрешённых точек в списках нет, модель сама ставит точки `goto` в левой половине («Иду
разведывать левую половину вручную»).

Оставшаяся неудача (medium-1003, одинаковая во всех вариантах) — решение исполнителя: выбран кандидат в
(0,35; −1,75), слева от границы, а исполнитель, подъезжая, перенёс цель на самое вероятное место в радиусе 0,7 м
и собрал образец при x = 0,79.

Цена варианта «каждый повод»: 122 обращения вместо 46 на шесть прогонов и меньший остаток заряда (8 против 17) —
робот дольше ищет в разрешённой половине. Дополнительные поводы без снятия четырёх секунд M3 не помогают (1 из 6).

### M4 — без счётчика штрафов модель путает штраф с потерей кандидата; со счётчиком — 8 из 8

Прогоны, где штраф был (все 12 сценариев; у модели штрафов меньше, потому что она иногда уезжает раньше):

| Вариант | Условие выполнено | Ложный возврат без штрафа (из 12 прогонов) |
|---|---|---|
| правило | 0 из 8 | — |
| модель | 4 из 6 | 5 |
| модель + поводы | 5 из 6 | 4 |
| модель, каждый повод | 5 из 5 | 6 |
| то же + счётчик штрафов | 8 из 8 | 0 |

Два разных сбоя:

1. **Не спросили вовремя.** hard-1003, штраф в 27,0 с; модель спрашивали 3,4 с назад, на повод `hazard` отвечает
   правило и ведёт к следующему кандидату. Модель получает слово в 33,2 с, после ещё одного сбора: «Тревога
   подтверждает штраф в (0.63; −0.43)… Штраф получен, значит по миссии прогон завершается» — верно, но на образец
   позже. То же в hard-1016.
2. **Не поняла — потому что ей не сказали.** medium-1001, 4,1 с, повод `candidate_lost`: «Триггер candidate_lost —
   потеря кандидата, это первый штраф… Продолжать разведку нельзя по условию миссии». Штрафа не было; робот
   вернулся с 0 из 5. Так закончились 5 прогонов из 12 (в трёх — на четвёртой секунде). В сводке состояния нет
   ни счётчика штрафов, ни списка событий, и модель судит по названию повода.

Со счётчиком (`"penalties": {"total": 1, "hazard_hit": 1, …}`) оба сбоя исчезли: 8 из 8 при штрафе, ни одного
ложного возврата, в четырёх прогонах без штрафа собрано всё (5/5, 5/5, 5/5, 7/7). Пример, hard-1024, 30,6 с, повод
`collision` (его даёт только флажок `mission_triggers`): «Штраф collision (total=1) получен в (-0.25;-0.10). Заряд
49.7, return_cost 4.7 — запас достаточен. Продолжать разведку нельзя по условию миссии.» После ложного сбора
(hard-1018): «Зарегистрирован false_collect (штрафов 1). Возврат обязателен.»

### M0 — контроль

Модель и правило дают одно и то же: 5 из 6, счёт 71,3 против 71,2. В варианте «каждый повод» счёт 73,7 и возврат
6 из 6 — за счёт одного сценария (hard-1002: правило разрядилось, модель вернулась с 7/7); в hard-1003 она же
собрала на образец меньше. На шести сценариях это не различие.

## Вывод

Гипотеза подтверждается для M1 (6 из 6 против 0 из 6) и M2 (5 из 6 против 0 из 6), для M3 в обвязке как есть —
нет (1 из 6 против 0 из 6: различие не показано). Сценариев шесть, это счёт прогонов, а не оценка доли.

Следует ли модель словесной миссии: да, в прочитанных ответах она каждый раз называет ограничение миссии и
выбирает цель по нему; текст миссии в сводке она ставит выше правил системного промпта. Не выполняется миссия
там, где модель не спросили или не сообщили нужного:

| Миссия | В обвязке как есть | Что мешает | Что поменять | Проверено |
|---|---|---|---|---|
| M1 | выполняется | — | — | 6 из 6 |
| M2 | выполняется, но с лишней осторожностью; срыв при тонком запасе | заряд между поводами модель не видит; оценки стоимости без запаса | порог возврата из миссии передавать исполнителю (он уже следит за зарядом каждую секунду) | не проверено; повод «заряд у порога» срыв не закрыл |
| M3 | не выполняется (1 из 6) | на треть поводов отвечает правило; исполнитель сдвигает цель и строит маршрут сам | отвечать моделью на каждый повод; запрет области передавать исполнителю как запретную зону маршрута | первое — 5 из 6; второе не проверено |
| M4 | 4 из 6 при штрафе и 5 ложных возвратов из 12 | на повод «штраф» отвечает правило; в сводке нет счётчика штрафов | каждый повод — модели; поле `penalties` в сводке; столкновение — повод | 8 из 8, ложных возвратов 0 |

Что показать жюри по критерию «качество LLM-планирования и промптов»:

- M1: одна фраза в миссии — и робот собирает ровно два образца и уезжает; правило так не может. Шесть из шести,
  с цитатой обоснования.
- M3 на одном сценарии (medium-1001) в двух вариантах: модель отказывается от кандидата справа, через полсекунды
  правило её перекрывает; без перекрытия робот не пересекает границу. Это честный показ и возможности, и того,
  где она теряется.
- M4: счётчик штрафов в сводке — пример того, что качество планирования определяется не только промптом, но и
  тем, что модели сообщают: без поля модель домысливает штраф по названию повода, с полем — 8 из 8.

Чего показывать не стоит: M2 как успех без оговорки (робот уезжает домой с 0–2 образцами) и счёт прежней миссии
как меру качества.

## Ограничения

- Шесть сценариев на миссию (для M4 — двенадцать), одна модель, один прогон на ячейку. Повторяемость держится на
  кэше ответов; без кэша модель может ответить иначе, разброс между ответами не измерен.
- Только быстрый симулятор; время ответа модели (18 с) роботу ничего не стоит. Вариант «каждый повод» в Gazebo
  означал бы втрое больше остановок (122 обращения вместо 46 на M3): его цена на настоящем роботе не измерена.
- Системный промпт не менялся: в нём прежняя миссия. Вариант промпта, где миссия подставляется в текст, не
  проверялся; возможно, он убрал бы лишнюю осторожность в M2.
- Повод «заряд у порога» с числом 30 сделан под M2 и срабатывает во всех миссиях; в M0, M3, M4 он задаёт модели
  лишний вопрос и меняет отдельные прогоны (M3 medium-1002: 5/5 вместо 4/5, оба не выполнены).
- Дополнительные сценарии M4 выбраны по наличию штрафа у правила; у модели в тех же сценариях штраф может не
  случиться. Счётчик штрафов проверен только на M4.
- Проверка M3 строга (допуск 1% точек пути) и считает позу по оценке агента, а не истинную. «Немедленно» в M4
  проверяется как «после штрафа ничего не собрано», время возврата не нормируется.
- «Выполнено» — необходимое условие, а не качество: пустой прогон (выехал и вернулся) выполняет M2, M3 и M4.
  Поэтому рядом приведены собранные образцы.
- Отступления от `PROTOCOL.md`, разрешённые заданием: обращения к модели по сети; опыт запускается своим
  скриптом, а не через `did.experiments`, файла `experiments/E#.yaml` нет; интервалов нет из-за шести сценариев.

## Как повторить

```
cd /Users/a/MAI/DID-research/R13
./px python -m pytest tests -q

# настройки и ключ модели читаются из /Users/a/MAI/DID/.env; ответы — из runs/_llm_cache (если он цел, сеть не нужна)
./px python tools/mission_eval.py --variants rule llm llm_triggers llm_ask --jobs 3
./px python tools/mission_eval.py --missions M4 --levels hard --seeds 1009 1013 1015 1016 1018 1024 \
    --variants rule llm llm_triggers llm_ask llm_ask_pen --jobs 3
./px python tools/mission_eval.py --missions M4 --variants llm_ask_pen --jobs 3

./px python tools/mission_eval.py --report                    # пересобрать runs/missions/summary.json
./px python tools/mission_tables.py                           # таблицы отчёта
./px python tools/mission_tables.py M3 llm medium-1001        # планы одного прогона с обоснованиями модели
```

Без кэша полный пересчёт — около 890 обращений к модели, примерно полтора часа при трёх одновременных запросах.
Каталог `runs/` в репозиторий не входит: записи прогонов и кэш ответов лежат только в этом рабочем дереве.
