# R13. Миссия словами — то, чего правило не умеет

## Вопрос

Меняет ли языковая модель поведение робота так, как сказано в миссии, если миссию задать другими словами —
без нового кода?
Правило (`HeuristicPlanner`) текст миссии не читает: его поведение от текста не зависит. Поэтому сравнение с
правилом здесь — контроль «что будет, если текст не читать», а не состязание двух способов выполнить миссию:
правило, в которое то же ограничение запрограммировали бы руками, в этой работе не делалось и не проверялось.

Миссии:

| № | Текст миссии | Что считается выполнением (везде ещё нужен возврат на базу) |
|---|---|---|
| M0 | прежняя: «Собери как можно больше образцов, избегай дорогих зон, вернись на базу до разрядки» | собран хотя бы один образец |
| M1 | «Собери ровно два образца и сразу возвращайся на базу» | собрано ровно два; домой робот повернул не позже 2 с после второго сбора; после второго сбора планировщик не назначил ни одной подцели на сбор |
| M2 | «Заряд важнее образцов: вернись на базу, сохранив не меньше 30 единиц заряда» | остаток заряда не меньше 30 |
| M3 | «Не заезжай в правую половину арены (x больше 0,5 м): работай только в левой» | истинная координата x центра робота ни на одном шаге симулятора (0,1 с) не больше 0,5 м; допуск 0 см |
| M4 | «После первого же штрафа немедленно возвращайся на базу» | домой робот повернул после первого штрафа и не позже 2 с после него |

Три исхода проверки: «выполнено», «не выполнено», «не проверено». «Не проверено» — когда проверять нечем или
не на чем: нет истинной траектории (M3), нет планов и режимов движения в записи (M1, M4), в прогоне не было
штрафа (M4). За успех «не проверено» не считается нигде.

Для M4 у прогона со штрафом три исхода: **вернулся из-за штрафа**; **возврат до штрафа** — домой робот повернул
раньше, чем получил штраф (провал, даже если штраф потом случился по дороге домой); **не отреагировал** — не
повернул или повернул позже 2 с.

«Когда робот повернул домой» берётся из записи прогона: это время последнего плана, если он начинается с
`return_base` (такое решение в обвязке необратимо), иначе — первая точка записи, с которой режим движения до
конца прогона «домой» (`did/mission_criteria.py`, `return_decision`).

Откуда 2 секунды. После сбора исполнитель сам стоит 1,0 с, такт агента 0,1 с, режимы пишутся раз в 0,2 с: до
1,3 с набегает без участия планировщика. 2 с — это с запасом, и вдвое меньше четырёх секунд, на которые
обвязка отдаёт поводы правилу: ответ, отложенный до следующего разрешённого вопроса, уже не «сразу». На итог
число не влияет в широких пределах: во всех прогонах, засчитанных как «вернулся из-за штрафа», задержка
0,0–0,1 с, во всех «не отреагировал» — 6,1 с и больше; в M1 задержка везде ровно 1,0 с.

## Гипотеза и что её опровергнет

Гипотеза: на миссиях M1–M3 робот с моделью выполняет условие миссии заметно чаще, чем робот с правилом.
Опровергает: доля прогонов, где условие выполнено, у модели не выше, чем у правила.

## Что сделано

Модель — `qwen3.8-flash-next` на сервере МАИ, ответ по JSON-схеме, запас на рассуждение 3000 токенов, ответы
кэшируются. Сценарии — шесть отложенных: medium и hard, номера 1001–1003. Для M4 этого мало (штраф у правила
случается только в двух из шести), поэтому добавлены шесть сценариев hard, где правило получает штраф:
1009, 1013, 1015, 1016 (опасная зона), 1018 (ещё и ложный сбор), 1024 (ещё и столкновение). Они выбраны по прогону
правила до запуска модели.

Варианты:

| Вариант | Что это |
|---|---|
| правило | `adaptive`, текст миссии не читает |
| модель | `adaptive_llm` в обвязке как есть |
| модель + поводы | то же и флажок `mission_triggers`: модель спрашивают ещё после столкновения и один раз, когда заряд опустился до «30 + дорога домой» |
| модель, каждый повод | то же и `llm_min_interval_s = 0`: на каждый повод отвечает модель, а не правило |
| то же + счётчик штрафов | то же и флажок `state_penalties`: в сводке состояния есть поле `penalties` (только для M4) |

Файлы:

- `did/agent.py` — в настройках агента: `mission` (текст миссии, по умолчанию прежний), `mission_triggers`,
  `mission_battery_floor`, `state_penalties` (все выключены). Текст миссии идёт в сводку состояния для планировщика.
- `did/planner.py`, `did/runner.py` — `LLMPlanner` берёт миссию из настроек агента, а не из константы.
- `did/mission_criteria.py` — тексты миссий и проверка «условие выполнено» по записи прогона.
- `did/recorder.py`, `did/runner.py` — по флажку `truth=True` в запись идёт истинная поза робота на каждом шаге
  симулятора (поле `truth`); без флажка запись прежняя.
- `did/llm_cache.py`, `did/llm.py` — режим «только кэш» и хранение отказов модели (см. «Исправления по ревью»).
- `tools/mission_eval.py` — прогон «миссия × вариант × сценарий» и сводка `runs/<каталог>/summary.json` по

  `tools/mission_cache_backfill.py` — перенос отказов модели из записей в кэш.
- `tests/test_missions.py` — 18 проверок, `tests/test_llm_clients.py` — ещё три на кэш.

Что исправлено в черновике предыдущего исполнителя:

- Прогон оборвался на M3 (2 из 6), M4 на модели и варианты с поводами не были посчитаны; в сводке была одна строка.
  Скрипт переписан: сводка собирается из записей, а не из памяти процесса, обрыв ничего не теряет.
- Повод «заряд у порога» тратился впустую: если модель спрашивали меньше 4 с назад, на него отвечало правило,
  а второй раз он не срабатывает. Теперь он ждёт, пока модель можно спросить. Число 30 вынесено из кода в настройку.
- В M4 прогон без штрафа засчитывался как выполненный без оговорки. Проверка та же, но в сводке отдельно
  считаются прогоны, где штраф был. (После ревью такой прогон — «не проверено», см. ниже.)
- Проверки M3 и M4 в той сдаче считали не то, что заявлено; это нашло ревью, см. «Исправления по ревью».

Поведение по умолчанию не изменилось: счёт правила на шести сценариях совпал с опытом E1 в основной ветке до

### Когда модель вообще получает слово

Планировщик вызывается только по поводам:

| Повод | Когда |
|---|---|
| `start` | начало прогона |
| `sample_collected`, `false_collect` | после сбора и после ложного сбора |
| `candidate_found`, `candidate_lost` | датчик показал новое место образца; место не подтвердилось |
| `subgoal_done`, `queue_empty` | план исполнен до конца |
| `hazard` | штраф в опасной зоне |
| `model_mismatch`, `sensor_degraded` | расход не сходится с прогнозом; датчик зашумел |

Чего в обвязке нет и что решает не модель:

1. **Четыре секунды.** Если модель спрашивали меньше 4 с назад (`llm_min_interval_s`), на повод отвечает правило.
   В прогонах варианта «модель» так принято 84 решения из 248 (34%); из 87 поводов «новый кандидат» модель
   ответила на 22, правило — на 65. Правило миссию не читает.
2. **Возврат по заряду** агент решает сам (`_check_return`): «заряд ≤ дорога домой × 1,1 + 4». Модель об этом не
   спрашивают. Порог «30 единиц» в M2 агенту неизвестен; между поводами модель заряд не видит.
3. **Маршрут** строит исполнитель: путь к разрешённой цели может пройти через запрещённую область. Подъезжая к
   кандидату, исполнитель сам переносит цель на самое вероятное место в радиусе 0,7 м.
4. **Столкновение** поводом не является; после ложного сбора в сводке нет слова «штраф». Поле `recent_events`
   всегда пусто, счётчика штрафов нет.
5. **Системный промпт** содержит прежнюю миссию и правило «не добавляй `return_base` на всякий случай». Новая
   миссия приходит только полем `mission` в сводке. В прочитанных ответах модель следовала полю `mission`.
6. Решение `return_base` необратимо: после него планировщик больше не вызывается.

Чего достаточно: для M1 — повода `sample_collected` (на него почти всегда отвечает модель: 82 из 84). Для M2 —
тех же поводов, если модель держит запас. Для M3 мешают пункты 1 и 3, для M4 — пункты 1 и 4.

### M1 — выполняет: 6 из 6 против 0 из 6

Во всех трёх вариантах модели собрано ровно 2 образца в каждом сценарии, остаток заряда 38–49. Правило собирает
5–7. «Сразу» теперь проверяется: во всех 18 прогонах модели домой робот повернул через 1,0 с после второго сбора
(это пауза самого исполнителя: решение принято на первом же вопросе), и ни одной подцели на сбор после второго
образца планировщик не назначил.

Пример, hard-1001, 27,7 с, повод `sample_collected`, ответ модели — `return_base`:
«Миссия: ровно 2 образца и сразу на базу. Собрано 2 из требуемых 2 — цель выполнена. Заряд 49.8, возврат 7.8,
запас огромный. Время 27.7 из 600. Дальнейшая разведка не нужна: миссия завершена.»
Робот поехал на базу и финишировал с 2 из 7 и зарядом 42.

## Коротко

Одна и та же программа ведёт робота по-разному в зависимости от текста миссии — без единой новой строки кода.
Миссию «собери ровно два образца и возвращайся» робот с моделью выполнил в **6 прогонах из 6**; «сохрани не меньше
30 единиц заряда» — в **5 из 6**, но ценой лишней осторожности: собрано 0–2 образца. Простое правило текст не читает и
не выполнило эти миссии ни разу.

Миссия «не заезжай в правую половину» в обычной обвязке сорвалась (1 из 6): на треть поводов вместо модели отвечает
правило, а оно запрета не знает. Когда на каждый повод отвечает модель — **5 из 6**. Миссия «после первого штрафа
сразу домой» — 4 из 6; если в сводку состояния добавить счётчик штрафов — **8 из 8** и ни одного ложного возврата.

Чего это не показывает: что модель лучше правила, в которое такое ограничение запрограммировали бы руками. Показано
одно: поведение меняется по тексту без нового кода. Сценариев шесть, по одному прогону — это счёт прогонов, а не доля.

Что показано. Одна и та же программа без единой новой строки кода ведёт робота по-разному в зависимости от

Чего это не показывает. Правило текст не читает, поэтому «модель N из 6, правило 0 из 6» не значит, что модель
лучше правила, в которое это ограничение запрограммировали бы руками. Такое правило («после второго сбора —
домой», «не ехать при x > 0,5») здесь не делалось; вполне возможно, оно выполняло бы эти миссии не хуже и
надёжнее. Измерено одно: модель меняет поведение по тексту без нового кода. Сценариев шесть, это счёт прогонов,
а не оценка доли.

Что показать жюри по критерию «качество LLM-планирования и промптов»:

- M1: одна фраза в миссии — и робот собирает ровно два образца и уезжает, без изменения кода. Шесть из шести,

- M3 на одном сценарии (medium-1001) в двух вариантах: модель отказывается от кандидата справа, через полсекунды

## Ограничения

- Шесть сценариев на миссию (для M4 — двенадцать), одна модель, один прогон на ячейку. Повторяемость держится на
  кэше ответов; без кэша модель может ответить иначе, разброс между ответами не измерен.
- Только быстрый симулятор; время ответа модели (18 с) роботу ничего не стоит. Вариант «каждый повод» в Gazebo
  означал бы втрое больше остановок (122 обращения вместо 46 на M3): его цена на настоящем роботе не измерена.
- Системный промпт не менялся: в нём прежняя миссия. Вариант промпта, где миссия подставляется в текст, не
  проверялся; возможно, он убрал бы лишнюю осторожность в M2.
- Повод «заряд у порога» с числом 30 сделан под M2 и срабатывает во всех миссиях; в M0, M3, M4 он задаёт модели
  лишний вопрос и меняет отдельные прогоны (M3 medium-1002: 5/5 вместо 4/5, оба не выполнены).
- Дополнительные сценарии M4 выбраны по наличию штрафа у правила; у модели в тех же сценариях штраф может не
  случиться. Счётчик штрафов проверен только на M4.
- Правила с запрограммированным ограничением миссии для сравнения нет; вывод — только о том, что модель меняет
  поведение по тексту.
- Многие ячейки разных вариантов — один и тот же прогон: пока запросы совпадают, кэш отдаёт тот же ответ
  (например, M1 одинакова во всех трёх вариантах модели, возврат на 4,1 с в M4 — один ответ на три варианта).
  Независимых наблюдений меньше, чем ячеек.
- Истинная траектория есть только в быстром симуляторе, шаг 0,1 с (робот за шаг проезжает не больше 2,2 см).
  Для записей Gazebo поля `truth` нет, там M3 даст «не проверено».
- «Сразу» в M1 и M4 — порог 2 с, выбранный под эту обвязку (обоснование — в разделе «Вопрос»); время ответа
  модели в быстром симуляторе роботу ничего не стоит, на настоящем роботе 18 с ответа в этот порог не уложатся.
- Причину возврата проверка не читает: «вернулся из-за штрафа» означает «повернул домой в течение 2 с после
  штрафа». Во всех таких прогонах решение принято на повод `hazard`, `false_collect` или `collision`, но
  совпадение по времени с возвратом по заряду проверка не отличила бы.
- Отказы модели в трёх прогонах (два пустых ответа, один обрыв связи) в кэш перенесены из записей прогонов, а
  не получены заново: повтор воспроизводит то, что случилось тогда, включая обрыв связи.
- «Выполнено» — необходимое условие, а не качество: пустой прогон (выехал и вернулся) выполняет M2 и M3.
  Поэтому рядом приведены собранные образцы.
- Отступления от `PROTOCOL.md`, разрешённые заданием: обращения к модели по сети; опыт запускается своим
  скриптом, а не через `did.experiments`, файла `experiments/E#.yaml` нет; интервалов нет из-за шести сценариев.

## Как повторить

```
cd /Users/a/MAI/DID-research/R13
./px python -m pytest tests -q

# Строгий повтор: ответы и отказы модели только из runs/_llm_cache. Сеть не используется, ключ и .env не нужны;
# запрос, которого в кэше нет, останавливает прогон ячейки, и она попадает в сводку как «ошибка запуска».
./px python tools/mission_eval.py --all --cache-only --out missions_strict --jobs 3      # 156 прогонов, около минуты
./px python tools/mission_eval.py --out missions_strict --compare missions               # сверка с исходными записями

./px python tools/mission_eval.py --out missions_strict --report         # пересобрать runs/missions_strict/summary.json
./px python tools/mission_tables.py missions_strict                      # таблицы отчёта
./px python tools/mission_tables.py missions_strict M3 llm medium-1001   # планы одного прогона с обоснованиями модели
```

Проверено: 156 из 156 ячеек посчитаны без ошибок и совпали с исходными записями; обращений к сети при этом 0
(счётчик сетевых вызовов в кэше не изменился: 575).

Каталог `runs/` в репозиторий не входит: записи прогонов (`runs/missions` — исходные, `runs/missions_strict` —
повтор с истинной траекторией) и кэш ответов лежат только в этом рабочем дереве. Без кэша строгий повтор
невозможен. Новый счёт по сети — те же команды без `--cache-only` (настройки и ключ модели — в
`/Users/a/MAI/DID/.env`): около 890 обращений к модели, примерно полтора часа при трёх одновременных запросах,
и ответы могут оказаться другими.

Если кэш был собран до этих исправлений, отказы модели в нём не лежат; их переносит из записей
`./px python tools/mission_cache_backfill.py` (сеть не нужна; в этом дереве уже выполнено, перенесено три отказа).
