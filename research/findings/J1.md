# J1. Модель решений Jev в роли быстрого сторожа миссии

## Вопрос

В R13 большая языковая модель (qwen3.8-flash-next) меняла поведение робота по тексту миссии, но каждый её ответ —
15 секунд и дольше, и всё это время робот стоит. Правило отвечает мгновенно, но текста миссии не читает.

Может ли модель решений Jev 1.13 (TypeSafe, класс «System One») закрыть этот разрыв: правило мгновенно предлагает
подцель, Jev за доли секунды отвечает «нарушает ли она миссию» — и робот выполняет миссию, заданную словами, не
простаивая?

Jev — не чат-модель. Она получает состояние (текст или JSON) и вопрос с заранее заданным набором ответов; возвращает
типизированный ответ с вероятностью и текста не пишет. Здесь использован один вид вопроса — «да/нет» (`noul`): ответ —
вероятность «да».

## Гипотеза и что её опровергнет

Гипотеза (сформулирована по заданию до итоговой серии; допуск «не хуже» числом заранее назван не был): правило под
присмотром сторожа Jev выполняет миссии M1–M4 по строгим критериям `did/mission_criteria.py` не реже, чем большая
модель, которую спрашивают по каждому поводу, а робот при этом простаивает на порядок меньше.

Опровергает любое из трёх:

- сторож выполняет миссии реже большой модели (по парам сценариев, критерий знаков);
- ответ Jev не быстрый: медиана больше секунды;
- Jev уверенно ошибается (вероятность «нарушает» не выше 0,35 там, где подцель миссию нарушает, или не ниже 0,8 там,
  где не нарушает) настолько часто, что миссии срываются из-за этого.

## Что сделано

### Доступ к Jev

Через OpenRouter Jev вызывается, но не через привычный адрес чата: у OpenRouter для таких моделей отдельный
«System One API». Найдено по открытым страницам до первого вызова (`openrouter.ai/typesafe/jev-1.13`,
`openrouter.ai/docs/guides/community/typesafe-sdk`, `docs.typesafe.ai`: System One, State, Primitives, Noul,
Confidence, API, Models, «Jev 1.13 jaggedness»).

```
POST https://openrouter.ai/api/v1/systemone
{"model": "typesafe/jev-1.13",
 "state": {...},                       # строка или JSON
 "questions": {"имя": {"type": "noul", "instructions": "...", "criteria": {"true": "...", "false": "..."}}}}
→ {"model": "typesafe/jev-1.13-20260917", "provider": "TypeSafe",
   "answers": {"имя": {"type": "noul", "noul": 0.93}},
   "usage": {"input_tokens": 283, "output_tokens": 20, "cost": 0.0000119}}
```

Ключ — обычный ключ OpenRouter; собственный ключ TypeSafe не понадобился. В одном запросе может быть много вопросов:
состояние читается один раз, вопросы оцениваются независимо. У вопроса «да/нет» отдельного поля уверенности нет —
только вероятность «да» (поле `confidence` есть у `choice` и `score`). Цена — 0,042 доллара за миллион входных
токенов, выходные бесплатны; пустой запрос с одним вопросом — 283 токена.

Первый вызов был один, пробный (283 токена, 0,0000119 долл., 1,3 с вместе с установкой связи, ответила
`typesafe/jev-1.13-20260917`); серии — после него.

### Клиент `did/llm_jev.py`

- Принимает только идентификатор `typesafe/jev-1.13`. Любой другой (`typesafe/jev-router`, `jev-latest`,
  `openrouter/auto`, другой регистр, пустой) отвергается до кэша, до учёта и до сети. Адрес сервера — константа, из
  окружения не берётся.
- Журнал расходов (после ревью — см. «Исправления по ревью») один на все рабочие деревья и лежит вне репозитория:
  `~/.did/jev_budget.json`, другой путь — переменная `DID_JEV_BUDGET_FILE`. Пока журнала нет, платный вызов
  запрещён: журнал создаёт человек отдельной командой, называя уже потраченную сумму. Перед каждой попыткой
  отправки клиент под блокировкой резервирует наибольшую возможную стоимость запроса; сумма «потрачено +
  зарезервировано» не поднимается выше 0,95 доллара. После ответа резерв заменяется стоимостью из ответа; попытка,
  которая могла дойти до сервера, но стоимости не сообщила, остаётся в журнале по оценке сверху отдельным полем.
  В первом круге (все числа этого отчёта) учёт был проще: файл `runs/_llm_budget/jev.json` в рабочем дереве.
- В ответе проверяется, кто ответил: годится только `typesafe/jev-1.13` или тот же идентификатор с датой выпуска,
  поставщик — TypeSafe. Иначе — ошибка, и в журнал пишется отметка `halted`: все следующие обращения отвергаются.
- Ключ читается из файла на время одного запроса; в объекте клиента, кэше, журнале, записях прогонов и текстах
  ошибок его нет. Ответ сервера — и успешный тоже — очищается от ключа, пока ключ ещё доступен, и из клиента
  выходит только проверенная схема: известные поля известных типов.
- Кэш `runs/_jev_cache/<хэш>.json` — по точному запросу (модель, состояние, вопросы); вместе с ответом хранится время
  настоящего вызова. Режим `strict=True` — «только кэш»: ни сети, ни ключа, ни журнала расходов, промах — ошибка
  `CacheMiss`.
- Соединение держится открытым между вызовами, поэтому время ответа — это время запроса, а не установки связи.

### Сторож `did/mission_guard.py`

Включается настройкой агента `mission_guard` (`''` — выключен, по умолчанию; `'jev'`; `'jev_llm'`). Одно решение:

1. Правило (`HeuristicPlanner`) предлагает подцель. Если оно и так едет домой — Jev не спрашивают.
2. Один запрос к Jev: вопрос «по миссии пора немедленно на базу?» и по вопросу «нарушит ли эта подцель миссию?» на
   каждую достижимую цель из сводки (обычно 4–6 целей) — один сетевой вызов на повод.
3. Вероятность «нарушит» не ниже 0,8 — подцель отброшена, правило предлагает следующую; не выше 0,35 — робот едет;
   между ними — сомнение: в режиме `jev` подцель отбрасывается (осторожный вариант), в режиме `jev_llm` решение
   целиком отдаётся большой модели. Отброшены все цели — правило само отвечает «на базу».
4. «Пора на базу» с вероятностью от 0,8 — возврат. Неуверенный ответ на этот вопрос решения не меняет: каждую цель
   сторож и так проверяет отдельно.

Если Jev недоступен (сеть, таймаут, потолок расходов, чужая модель в ответе, ответ не по схеме), поведение задаёт
настройка запасного режима. Для показа он включён: сторож отключается до конца миссии, дальше решает одно правило, а
в журнал решений пишется причина — «Сторож миссии отключён: …; миссия словами дальше не гарантируется». В
исследовательских прогонах (`tools/jev_eval.py`) он выключен: отказ Jev останавливает прогон, чтобы числа сторожа
не смешивались с ездой по правилу. Промах кэша в режиме «только кэш» останавливает прогон всегда.

Что получает Jev: текст миссии как есть (по-русски) и несколько чисел, одинаковых для любой миссии, — сколько образцов
собрано, сколько штрафов получено, заряд, сколько заряда останется на базе, если ехать домой сейчас и если сначала
выполнить подцель, координаты цели. Какое из чисел важно для миссии и с чем его сравнивать, код не знает: ни «два»,
ни «30», ни «0,5 м» в коде сторожа нет. Арифметику («заряд после подцели и дороги домой») считает код — по
документации Jev считать не умеет.

Пример запроса (итоговая формулировка):

```
state:  {"mission": "Не заезжай в правую половину арены (x больше 0,5 м): работай только в левой.",
         "robot": "The robot has collected 1 samples so far. The robot has received 0 penalties so far. The battery of
                   the robot now holds 50.0 units. If the robot drives back to base right now, it arrives with 41.6
                   units of battery left."}
вопрос: {"proposed_action": "The robot will drive to the target and collect a sample there. The target is at
                             x = 1.2 m, y = 0.0 m. After that and the drive home the robot will arrive at base with
                             38.5 units of battery left.",
         "question": "Does performing `proposed_action` now contradict `mission`? Judge only by what the mission text
                      explicitly limits or forbids; facts that the mission does not mention do not matter."}
```

Врезки в существующий код: `did/agent.py` — две настройки (`mission_guard`, `guard_wait`), счётчик штрафов в сводке
при включённом стороже, ожидание ответа и запись решения сторожа в план (8 строк); `did/runner.py` — сборка
планировщика со сторожем (4 строки). `did/planner.py` не менялся: сторож оборачивает правило снаружи.

### Подбор формулировок (сценарии 1–20)

Состояния для подбора — 696 решений правила на сценариях 1–20 (medium и hard), собранных без сети. Для каждого
известна правда по критерию миссии: M1 — после второго сбора любая работа нарушает миссию; M2 — на базе останется
меньше 30; M3 — цель правее x = 0,5 м; M4 — штраф уже был. Вопрос «нарушит ли подцель», по 40 состояний на миссию
(около 790 ответов на формулировку):

| Формулировка | Что в ней | Уверенно неверно | Сомнений | Что не так |
|---|---|---|---|---|
| v1 | факты и подцель — числа в JSON; вопрос «нарушит ли правило миссии» | 0 | 203 | M2: половина ответов — сомнение (93 из 202): число «25,5» с порогом «30» Jev не сравнивает |
| v2 | то же, вопрос буквальнее («судить только по тому, что миссия прямо ограничивает») | 0 | 178 | M2 стало хуже: уверенное «да» — 3 из 95 |
| v3 | вопрос v2, но факты и подцель — фразами по-английски | 1 | 83 | M2 выправилась (сомнений 10 из 202); M3: сомнения, когда сам робот стоит в правой половине |
| v4 | v3 и отбор фактов: Jev сам отвечает, о чём миссия, и получает только эти факты | 11 | 94 | M3: 11 уверенных ошибок; M1: уверенность упала |
| **v5** | v3 без положения самого робота (вопрос — о цели) | 0 | 35 | остались сомнения M2 у самого порога и M1 (вероятности 0,21–0,29 при правде «нет») |

Счёт в таблице — при порогах 0,2 и 0,8. Пороги 0,35 и 0,8 выбраны по распределению v5: у ответов о подцелях с
правдой «нет» вероятность не выше 0,30, порог взят сразу над ними. Проверка при этих порогах на второй выборке (по 80 состояний
на миссию, 1 533 ответа о подцелях): уверенных ошибок 0, сомнений 23, все в M2.

Замкнутый прогон на сценариях 1–5 (medium и hard, 10 сценариев на миссию) показал ещё одно: в M2 сторож пропускал
подцели «впритык» (оценка 30,6 при пороге 30), а робот приезжал с 21–27: оценка расхода оказывалась ниже
настоящего. Поэтому сторожу передаётся осторожная оценка заряда — с тем же запасом, с которым агент сам решает,
достижима ли цель (дорога домой ×1,1 и ещё 4 единицы). После этого на сценариях 1–5: M1 10 из 10, M2 10 из 10
(было 7), M3 8 из 10, M4 2 из 3 прогонов со штрафом; M0 — как у правила.

Числа этого раздела — из журнала подбора. Ответы на v1–v4 лежат в кэше для состояний с прежней оценкой заряда;
повтор `--tune` для них сейчас сделал бы новые обращения (около 0,01 доллара на формулировку).

После этого формулировка, пороги и код сторожа заморожены (коммит `446ca0c`), и итоговая серия со сторожем
посчитана один раз. Позже менялся только инструмент прогонов и сводки (`tools/jev_eval.py`): парные сравнения,
проверка «с учётом времени ответа», срок ответа большой модели.

### Итоговая серия

Сценарии 1101–1110, medium и hard: 20 сценариев на миссию, до этого не запускались ни разу. Варианты:

| Вариант | Что это |
|---|---|
| правило | `adaptive`; текст миссии не читает |
| большая модель | qwen3.8-flash-next на каждый повод — лучший вариант R13 (`llm_ask_pen`): поводы «столкновение» и «заряд у порога», счётчик штрафов в сводке; схема ответа, запас на рассуждение 3000 токенов |
| сторож Jev + правило | `mission_guard='jev'`, те же дополнительные поводы |
| сторож Jev + большая модель | `mission_guard='jev_llm'`: сомнительные случаи решает большая модель |
| те же два с ожиданием в симуляторе | `guard_wait=True`: после каждого решения робот стоит столько, сколько длился ответ Jev (и большой модели, если её спросили) |

В основных четырёх вариантах, как в R13, мир на время ответа модели стоит: это качество решений в чистом виде.
Колонка «с учётом времени ответа» — та же проверка, в которой решение о возврате на базу отнесено на момент, когда
ответ пришёл (время вопроса плюс длительность ответа): от этого зависят только условия «сразу» в M1 и M4. Для
большой модели это пересчёт, а не прогон (в настоящем прогоне с ожиданием робот оказался бы в другом месте); для
сторожа есть и настоящий прогон с ожиданием.

Объём: 520 ячеек «миссия × вариант × сценарий» (M1–M4 × шесть вариантов × 20 и M0 × два варианта × 20).
Заранее оценено: около 12 поводов на прогон, около 1 200 токенов на запрос (0,00005 долл.) — на 340 прогонов со
сторожем около 4 000 запросов и 0,2 доллара, вместе с уже потраченным на подбор (0,13) — около 0,35 доллара; в
потолок укладывается с запасом, серию сокращать не пришлось. На деле вышло 1 687 запросов и 0,10 доллара: одинаковые
запросы разных вариантов берутся из кэша.

Проверки — `tests/test_jev_guard.py`, 34 штуки (после ревью; было 13), сеть подменена, журнал расходов и домашний
каталог — временные. Клиент: чужая модель отвергается до отправки (девять идентификаторов, включая
`typesafe/jev-router`); без журнала расходов, с пустым или испорченным журналом запрос не уходит; команда создания
журнала переносит потраченное и не даёт обнулить счёт; резерв держит «потрачено + зарезервировано» под потолком, в
том числе у четырёх одновременных клиентов и у двух отдельных процессов; учитывается каждая попытка, которая могла
дойти до сервера, в том числе неудачные перед успехом; неизвестная стоимость считается по оценке сверху отдельным
полем; сбой посреди записи не портит журнал, чтение его не меняет; ответ чужой модели останавливает все следующие
обращения и в кэш не попадает; ключ не попадает в кэш, журнал, ошибки и объект клиента — ни из ответа с ошибкой, ни
из успешного ответа (семь мест, где сервер может его вернуть); режим «только кэш» не читает ключ и не трогает
журнал, и `--cache-only` доходит до каждого места, где инструмент создаёт клиента. Сторож: отбрасывает нарушающую
подцель, возвращает робота, передаёт сомнение большой модели, не спрашивает Jev, когда правило и так едет домой; с
выключенным флажком и со сторожем, который всё разрешает, счёт прогона тот же; на каждый из семи видов отказа Jev
в запасном режиме отключается и оставляет правило, а без запасного режима останавливает прогон.

Не сломано: `./px python -m pytest -q -p no:cacheprovider` — 777 passed, 1 skipped после вливания main (в main 743 проверки, здесь к ним 34 проверки J1); пересчёт E1 в этом дереве в первом круге
совпал со сводкой `/Users/a/MAI/DID/runs/E1/summary.json` во всех полях, кроме времени создания.

Числа — из `runs/J1/summary.json`. Сценариев 20 на миссию, по одному прогону; сравнения — по парам сценариев,

### Выполнение миссий

«Выполнено» — строгий критерий R13, мир на время ответа стоит. «С учётом времени ответа» — то же, но решение о
возврате отнесено на момент, когда ответ пришёл. «Не проверено» в M4 — прогоны без штрафа. «Простой» — сумма
зарегистрированного времени ответов моделей за прогон, то есть возможный простой: столько робот стоял бы, если бы
ждал каждый ответ. В этих прогонах он не стоял (мир на время ответа остановлен); настоящее ожидание есть только в

- Сомнений о подцелях — 66 из 9 229 (0,7%): 63 в M2 (во всех правда — «нарушит», оценка заряда от 18 до 29,9) и 3
  в M0. Большой модели из них
  ушло 13 решений: сомнение передаётся, только если оно касается той цели, которую правило выбрало бы первой.
- Вопрос «пора ли на базу» работает там, где миссия называет событие (M1 — 40 из 40, M4 — 10 из 10, ложных
  срабатываний нет), и не работает в M2: «пора» там следует из арифметики по всем целям, и Jev отвечает «нет»
  (52 из 52 неверно). На исход это не влияет: в M2 робота возвращает проверка целей, а не этот вопрос.

### Где Jev ошибается

1. **Числа у порога (M2).** Обе неудачи M2 — пропущенные подцели, после которых на базе по осторожной оценке
   оставалось меньше 30: в medium-1101 Jev ответил 0,18 на «останется 24,9» и 0,25 на «останется 27,2» (робот
   приехал с 21,1), в hard-1102 — 0,29–0,33 на «останется 29,3» и 0,15–0,17 на «останется 29,1» (приехал с 25,0,
   по дороге ещё штраф в опасной зоне). Те же числа в соседних запросах Jev оценивал верно (27,4 → 0,88): ответ у
   порога зависит от того, какие ещё числа стоят рядом. Документация предупреждает об этом прямо («Jev не
   калькулятор; сравнение чисел оставляйте коду»). Вдали от порога ошибок нет.
2. **Форма подачи важнее формулировки вопроса.** Те же числа в JSON давали в M2 сомнение в половине ответов; фразой
   («приедет на базу с 25,5 единицами») — уверенный ответ. Положение самого робота в состоянии сбивало M3: когда
   робот стоял в правой половине, Jev считал нарушением любую подцель, даже слева.
3. **Вероятности не откалиброваны в прямом смысле** (см. выше): пороги пришлось подбирать по данным, а не брать
   «0,5».
4. **Чего Jev не видит.** Он судит цель, а не дорогу к ней и не то, куда исполнитель перенесёт цель: все три неудачи
   M3 и неудачи M4 — не его ответы.

Сбоев самого сервиса в итоговой серии не было: 0 неудачных обращений из 1 687. За всю работу одно — обрыв TLS до
openrouter.ai в начале подбора (связь пропадала на несколько минут).

## Коротко

Обычная языковая модель пишет текст: ей дают описание ситуации, она рассуждает и отвечает словами — у нас это 20
секунд на ответ. Модель решений (Jev) текста не пишет. Ей дают описание ситуации и вопрос, на который можно ответить
только «да» или «нет» (или выбрать из готового списка), и она за полсекунды возвращает вероятность «да». Она не
планирует и не объясняет — она быстро судит одно узкое утверждение.

В роботе она работает сторожем. Простое правило мгновенно предлагает, куда ехать, а Jev читает текст миссии и
отвечает, не нарушит ли эта поездка миссию. Уверенно «не нарушит» — робот едет; уверенно «нарушит» — правило
предлагает следующую цель или робот возвращается на базу. Отдельно Jev спрашивают, не пора ли по миссии домой.

Что получилось на 20 новых сценариях в быстром симуляторе. Миссию «собери ровно два образца» сторож выполнил в 20
прогонах из 20 (правило — 0 из 20), «сохрани 30 единиц заряда» — в 18, «не заезжай в правую половину» — в 17,
«после штрафа домой» — в 4 из 5 прогонов, где штраф был. У большой модели — 20, 20, 17 и 4 из 6. На этой серии
результаты близки; равноценность не установлена, у Jev две дополнительные неудачи в миссии про заряд. Медиана
зарегистрированного ответа Jev — 402 мс (по 3 395 использованным ответам, включая взятые из кэша); большая модель
отвечает около 20 секунд. Сумма времени ответов за прогон — 4 секунды у сторожа и 5 минут у большой модели: это
возможный простой, полного прогона большой модели с настоящим ожиданием не было. Если отнести решение на момент,
когда ответ пришёл, условие «сразу домой» у большой модели выполнено в 1 прогоне из 20, у сторожа — в 19. Стоит это
0,0006 доллара за прогон; на всю работу ушло 23 цента. Ошибается Jev там, где нужно сравнить числа у самого порога
(«останется 29,3» при требовании «не меньше 30»): обе неудачи с зарядом — отсюда. Ещё три неудачи — не его:
исполнитель сам заехал за черту по дороге к разрешённой цели. Передавать сомнительные случаи большой модели почти
не пришлось (1,6% решений) и пользы это не дало. Если Jev недоступен, на показе сторож отключается и робот едет по
правилу, о чём пишет в журнал; миссия словами при этом не выполняется.

Строка для слайда: «В быстром симуляторе сторож Jev выполнил миссию „ровно два образца“ в 20 сценариях из 20 против
0 из 20 у правила; медиана зарегистрированного ответа — 402 мс».

## Вывод

Гипотеза в заявленном виде не доказана: на этой серии результаты сторожа и большой модели близки, равноценность не
установлена, у Jev две дополнительные неудачи в M2. Ни одно из трёх заранее названных опровержений не сработало,
но «не опровергнута на 20 сценариях» — это меньше, чем «подтверждена».

- **Выполнение миссий.** Сторож Jev + правило против большой модели по парам сценариев: M1 — 20 и 20 из 20, M3 —
  17 и 17 (одни и те же сценарии), M4 — 5 общих сценариев со штрафом, 3 выполнены у обоих, 1 только у сторожа
  (p = 1). M2 — 18 против 20, два сценария в пользу большой модели, p = 0,5: различие не показано, но p = 0,5
  равноценности не доказывает — допуск «не хуже» заранее не назывался, а обе неудачи — настоящие ошибки Jev.
  Против правила сторож выигрывает в M1–M3 (20, 17 и 17 сценариев против 0, p < 0,001); в M4 на 4 общих сценариях
  со штрафом — 3 победы и 0 поражений, p = 0,25: этого мало, чтобы утверждать превосходство.
- **Скорость.** Зарегистрированный ответ Jev — 402 мс по медиане (3 395 использованных ответов, включая взятые из

- **Передача сомнений большой модели** не нужна в нынешнем виде: 1,6% решений, результат тот же, сумма времени

Практически: текст миссии можно отдать читать быстрой модели решений, а правилу оставить выбор цели. На четырёх
простых миссиях в быстром симуляторе это дало результаты, близкие к большой модели, при ответе в доли секунды;
робот при этом всё равно ждёт каждый ответ сторожа — около 0,4 секунды на решение. Числовые пороги из текста
миссии («не меньше 30») надёжнее один раз извлечь и сравнивать в коде, чем каждый раз спрашивать у Jev.

## Ограничения

- **Платные вызовы закрыты (решение ведущего после второго круга ревью, 8.10).** Журнал расходов вне репозитория не
  создан, и без него клиент отвергает любой платный запрос до отправки. Ревью второго круга: потолок 1 доллар кодом
  клиента строго не гарантируется — резерв перед запросом есть оценка сверху, и если сервер насчитает больше резерва,
  это выяснится уже после оплаты (в проверке: расход 0,949, ответ ценой 0,06 — итог 1,009). На 3 963 записанных
  ответах настоящая цена не превышала 14 % резерва, но строгую гарантию даёт только предел оплаты на стороне
  поставщика (лимит на ключ). Там же найдено: исключение транспорта может вынести строку ключа в сообщение об
  ошибке и в журнал решений при запасном режиме; неполный журнал расходов допускает отправку; ключ читается до
  проверки бюджета. Эти три места исправляются отдельной правкой; до неё и до лимита на ключ платные вызовы не
  включать. Числа исследования от этого не зависят: они получены в первом круге и пересчитываются из записей.

- Четыре миссии, каждая — одно простое условие. Составные условия, отрицания, миссии, требующие плана из нескольких
  шагов, не проверялись; по документации Jev на них слабее.
- Сторож только запрещает и возвращает: предложить цель, которой нет в списке правила (как большая модель в R13
  ставит точки `goto` в разрешённой половине), он не может. Отсюда меньше образцов в M3, чем у большой модели
  (2,35 против 2,90).
- Jev получает числа, которые выбрал и посчитал код (собрано, штрафы, заряд после подцели, координаты цели), и
  осторожную оценку заряда с запасом агента. Миссия о чём-то другом (время, конкретные зоны грунта) потребует
  добавить факты; запас 1,1 и 4 единицы подобран под агента и проверен только на M2.
- Правда для калибровки — критерий миссии, приложенный к числам состояния: для M2 это оценка агента, а не
  настоящий расход; для M3 — координата цели, а не путь. Поэтому «Jev не ошибся в M3» и «3 прогона M3 не выполнены»
  не противоречат друг другу.
- Формулировки и пороги подобраны на сценариях 1–20 под эти же четыре миссии. Итоговые сценарии новые, но миссии те
  же: как сторож поведёт себя на миссии, которой при подборе не было, не измерено. Тексты миссий русские, вопросы
  английские; другие сочетания не проверялись.
- Равноценность сторожа и большой модели не установлена: критерий знаков на 20 сценариях различие в два прогона
  (M2) не отличает от нуля, но и «не хуже» не доказывает. Допуск заранее назван не был.
- Время ответа: медиана 402 мс посчитана по 3 395 использованным ответам, из которых по сети получено 1 687,
  остальные взяты из кэша с временем первого вызова (по 1 710 разным запросам медиана 406,5 мс). «Простой» — сумма
  зарегистрированного времени ответов, то есть возможный простой; полного прогона большой модели с настоящим
  ожиданием не было, поэтому «4,2 с против 314 с» — сравнение времени ответов, а не измеренных стоянок.
- Потолок расходов защищён оценкой сверху: резерв на запрос — (байты запроса + 1 024) токенов по двойной цене. На
  3 963 записанных ответах настоящая стоимость ни разу не превысила резерв (наибольшая — 14% резерва). Если сервер
  насчитает больше резерва, клиент запишет стоимость и остановит работу, но этот запрос уже оплачен: на такой
  случай оставлен запас между остановкой (0,95) и потолком (1,00). Журнал — локальный файл: расходы с другой
  машины или другим ключом он не видит; настоящий счёт — на стороне OpenRouter.
- Резерв оборванного процесса (убит между резервом и ответом) остаётся в журнале и считается занятым: это безопасно,
  но снять его может только человек, поправив файл.
- В запасном режиме (Jev недоступен) робот едет по правилу и миссию словами не выполняет: это сохранение показа, а
  не выполнение миссии. Проверен подменёнными отказами в быстром симуляторе; на настоящем обрыве связи не проверялся.
- Сценариев 20 на миссию, по одному прогону; для M4 прогонов со штрафом 4–8, общих сценариев со штрафом у пары
  вариантов — 4–5. Многие ячейки вариантов «сторож» и
  «сторож + большая модель» — один и тот же прогон (в M1, M3, M4 совпадают полностью).
- Колонка «с учётом времени ответа» для большой модели — пересчёт, а не прогон: в настоящем прогоне с ожиданием
  20 с на решение робот оказался бы в другом месте (цена такого ожидания измерена в R3). Прогоны с настоящим
  ожиданием сделаны только для сторожа. В них на время ответа сдвигается начало движения, а решение принимается по
  состоянию на момент вопроса.
- Время ответа Jev измерено с ноутбука через OpenRouter при трёх одновременных запросах; на роботе и на другом
  канале оно будет другим. Связь с OpenRouter отсюда временами пропадает на минуты: на показе сторож в этом случае
  отключается до конца миссии (запасной режим), в исследовательских прогонах ошибка Jev останавливает прогон.
- Только быстрый симулятор; Gazebo не запускался.
- Большая модель посчитана в два прохода из-за отказов сервера (см. «Результат»); время её ответа включает очередь
  сервера МАИ под нагрузкой соседних работ.
- Повтор «только кэш» воспроизводит 517 ячеек из 520 в точности. Не воспроизводятся три ячейки M2 с передачей
  большой модели: в одной отличается только простой, две с ожиданием в симуляторе идут другой дорогой (время
  ожидания большой модели в записи включает неудачные попытки, которых в кэше нет) и останавливаются на промахе кэша.
- Отступления от `PROTOCOL.md`, разрешённые заданием: обращения к моделям по сети, платная модель; опыт запускается
  своим скриптом, файла `experiments/E#.yaml` нет; вместо интервалов — счёт прогонов и критерий знаков.

## Исправления по ревью

Вердикт независимого ревью — «можно после исправлений»: основная таблица при пересчёте 520 записей воспроизвелась,
утечки скрытой правды в запросах к Jev нет, с выключенным сторожем обычные агенты дают прежние числа. Семь находок и
что с ними сделано. Платных вызовов при исправлениях не было: всё проверено подменённым транспортом и кэшем.

1. **Потолок 1 доллар не был обеспечен.** Бюджет проверялся отдельно от запроса: два клиента при расходе 0,949
   оба проходили проверку; отсутствующий файл учёта означал нулевой расход; запись могла потерять счётчик при
   сбое. Сделано: один журнал на все рабочие деревья вне репозитория (`~/.did/jev_budget.json`, путь меняется
   переменной `DID_JEV_BUDGET_FILE`; каталог создаётся с правами только владельца); отдельный файл блокировки;
   запись заменой файла (временный файл, fsync, rename), чтение журнал не меняет; перед каждой попыткой под
   блокировкой резервируется наибольшая возможная стоимость запроса, и «потрачено + зарезервировано» не
   поднимается выше 0,95; отсутствующий, пустой или испорченный журнал запрещает платный вызов; журнал создаётся
   только явной командой с уже потраченной суммой и повторно не создаётся (обнулить счёт нельзя). Проверки: отказ
   без журнала; перенос суммы; случай из ревью (0,949 и запрос до 0,04 — отказ); четыре одновременных клиента на
   последние деньги — проходит один; два отдельных процесса с общим журналом останавливаются ровно на 0,95; сбой
   посреди записи оставляет прежний журнал.
2. **Успешный повтор скрывал стоимость предыдущих попыток.** Сделано: резерв и итог — у каждой попытки. Связь не
   установилась — резерв снимается; сервер отказал (4xx) — попытка учтена с нулевой стоимостью; таймаут чтения,
   обрыв, 5xx, ответ не в JSON или без поля стоимости — попытка учтена по оценке сверху в отдельном поле
   `unknown_cost_usd` (счётчик `unknown_attempts`). Проверка — случай из ревью: таймаут, потом успех ценой 0,00002 —
   в журнале две попытки, одна с неизвестной стоимостью.
3. **Вымарывание ключа не покрывало успешные ответы.** Сделано: текст ответа очищается от ключа внутри функции
   отправки, пока ключ доступен; из неё выходит только проверенная схема (идентификаторы модели и поставщика из
   разрешённых знаков, счётчики, стоимость, ответы известных типов; неизвестные поля отбрасываются); в `halted` и
   в ошибки сырые строки сервера не пишутся — только постоянный текст и очищенный обрезанный идентификатор;
   вымарывание идёт до обрезки (раньше обрезка могла оставить кусок ключа). Проверки для HTTP 200: ключ в `model`,
   в `provider`, вместо ответов, в имени ответа, вместо вероятности, в типе ответа, в лишних полях — нигде не
   попадает в ошибку, журнал и кэш.
4. **`--cache-only` игнорировался при подборе.** Сделано: клиент в `tools/jev_eval.py` создаётся в одном месте
   (`make_jev`), режим передан и в прогоны, и в `--tune`; с `--cache-only` дополнительно выставляется переменная
   `DID_JEV_CACHE_ONLY=1`, которая делает «только кэш» любым клиентом процесса; такой клиент не хранит путь к
   ключу, не читает ключ и не трогает журнал. Проверка: `--tune … --cache-only` при «доступном» ключе на промахе
   кэша останавливается ошибкой, ключ не прочитан, запрос не ушёл. То же на настоящем кэше: `--tune v5 --cache-only`
   останавливается на промахе (ответов подбора для нынешних состояний в кэше нет).
5. **Парный критерий M4 считал непроверенный прогон проигрышем.** Сделано: сравниваются только сценарии, где исход
   проверен у обоих вариантов; в таблице показаны общие сценарии, проверенные у обоих и выполненные у обоих. M4:
   сторож против правила — 4 пары, 3 победы, 0 поражений, p = 0,25 (было 0,125); сторож против большой модели —
   5 пар, 1 победа, 0 поражений, p = 1. Остальные числа отчёта при пересчёте из записей не изменились.
6. **Вывод был сильнее данных.** «Гипотеза подтверждается», «то же следование миссии», «без остановок робота»
   убраны; написано, что результаты близки, равноценность не установлена, у Jev две дополнительные неудачи в M2;

7. **Запасного режима для показа не было.** Сделано: при отказе Jev сторож отключается до конца миссии, дальше

## Как повторить

```
cd /Users/a/MAI/DID-research/J1
./px python -m pytest -q -p no:cacheprovider                 # сеть и домашний каталог не трогает
./px python -m did.llm_jev                                   # журнал расходов и размер кэша

# Повтор итоговой серии без сети и без денег: ответы Jev — из runs/_jev_cache, большой модели — из runs/_llm_cache.
./px python tools/jev_eval.py --final --missions M0 M1 M2 M3 M4 --variants rule jev --jobs 2 --cache-only
./px python tools/jev_eval.py --final --variants jev_wait jev_llm jev_llm_wait llm --jobs 2 --cache-only
./px python tools/jev_eval.py --out J1 --report              # только сводка runs/J1/summary.json и таблицы

# Подбор (сценарии 1–20)
./px python tools/jev_eval.py --collect                      # состояния, без сети
./px python tools/jev_eval.py --tune v5 --per-mission 80 --sample-seed 7 --cache-only
./px python tools/jev_eval.py --out J1_dev --seeds 1 2 3 4 5 --missions M0 M1 M2 M3 M4 --variants rule jev --cache-only
```

Каталог `runs/` в репозиторий не входит: записи прогонов и кэш ответов Jev и большой модели лежат только в этом
рабочем дереве; без них повтор «только кэш» невозможен. С `--cache-only` ключ не читается, журнал расходов не
нужен, промах кэша останавливает прогон.

Подбор из кэша сейчас не повторяется: `--tune v5 … --cache-only` останавливается на первом же запросе ошибкой
`CacheMiss` (проверено для выборок 0 и 7). Состояния для подбора после введения осторожной оценки заряда другие,
и ответов на них в кэше нет; числа раздела «Подбор формулировок» взяты из журнала подбора первого круга. Это ровно
тот случай из ревью: до исправления такая команда при доступном ключе ушла бы в сеть за деньги. Итоговая серия из
кэша повторяется: проверено на M1 и M2 со сторожем (40 прогонов, все поля сводки совпали).

Новый счёт по сети — те же команды без `--cache-only`. Для него нужны три вещи.

- **Ключ.** Переменная окружения `DID_JEV_KEY_FILE` — путь к файлу строк `ИМЯ=значение` со строкой
  `OPENROUTER_API_KEY=…`. Ни ключа, ни пути к нему в репозитории нет; файл читается на время одного запроса.
- **Журнал расходов.** По умолчанию `~/.did/jev_budget.json` — один на все рабочие деревья; другой путь задаётся
  переменной `DID_JEV_BUDGET_FILE`. Журнал создаётся один раз командой, которой называют уже потраченное (сумма и
  число обращений — из учёта первого круга `runs/_llm_budget/jev.json`):

  ```
  ./px python -m did.llm_jev --init-budget --spent 0.226192974 --calls 3964 --input-tokens 5385547 --output-tokens 419017 --failed-calls 1
  ```

  Без неё любой платный вызов отвергается до отправки с ошибкой «журнала расходов на Jev нет … платный вызов
  запрещён». Повторный запуск команды журнал не меняет и отвечает отказом. Клиент откажет, когда «потрачено +
  зарезервировано» вместе с новым запросом превысило бы 0,95 доллара.
- **Большая модель.** Настройки сервера МАИ — из `/Users/a/MAI/DID/.env`.

С этой машины связь с openrouter.ai временами обрывается на несколько минут (обрыв TLS); клиент повторяет запрос до
пяти раз, и каждая попытка, которая могла дойти до сервера, учитывается в журнале.
